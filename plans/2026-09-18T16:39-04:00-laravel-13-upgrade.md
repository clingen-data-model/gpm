# Upgrade to Laravel 13

## Context

Follow-up to the Laravel 12 upgrade already landed on `composer-updates-202609` (now on `laravel/framework ^12.0`, locked v12.69.2). Per the [official Laravel 13 upgrade guide](https://laravel.com/docs/13.x/upgrade), Laravel itself estimates "10 minutes" — but this repo's actual blast radius is materially bigger than the Laravel 12 upgrade, because two heavily-used ecosystem packages are forced into **major** version bumps as a side effect, each with real breaking changes that touch this codebase's custom code.

**Feasibility confirmed live** (not just in theory): a `composer require --dry-run --with-all-dependencies` against the real Packagist registry today resolves cleanly to a full working set — `laravel/framework` v13.32.0, `laravel/tinker` v3.0.2, `phpunit/phpunit` v12.5.35, `laravel/fortify` v1.39.0, `laravel/sanctum` v4.3.3, `laravel/telescope` v5.24.0, `laravel/sail` v1.67.0, `nunomaduro/collision` v8.9.5 (its conflict rule against Laravel 13 was relaxed in a later 8.x patch — no major bump needed), `lab404/laravel-impersonate` 1.7.8, `laravel/slack-notification-channel` v3.10.0, `lorisleiva/laravel-actions` v2.12.0, `rap2hpoutre/laravel-log-viewer` v3.1.0, `spatie/laravel-ignition` v2.12.0, and the two majors: **`spatie/laravel-permission` v6.24.0 → v8.3.0** and **`spatie/laravel-activitylog` v4.10.2 → v5.1.1**. Of these, only 5 packages' `composer.json` constraints actually need editing — the rest already resolve to newer compatible releases within their existing `^` constraints once `--with-all-dependencies` is used (confirmed by the dry run, not assumed).

New transitive deps get pulled in by Fortify's newer release (`laravel/passkeys`, `laravel/sentinel`, `web-auth/webauthn-lib` and friends — WebAuthn/passkey support). These are optional Fortify features, not auto-enabled by installing them — verify `route:list` doesn't unexpectedly grow during verification, but no code change is planned around them.

### High-impact guide items

1. **Dependency updates** — see above.
2. **CSRF middleware rename**: `Illuminate\Foundation\Http\Middleware\VerifyCsrfToken` → `PreventRequestForgery`, which also adds a `Sec-Fetch-Site`-header origin check on top of the token check. This app still uses the legacy `app/Http/Kernel.php` style (not `bootstrap/app.php`'s `withMiddleware()`), with direct references at `app/Http/Kernel.php:38` and `config/sanctum.php:47` that need updating (old alias still works but the guide recommends updating direct references). The new origin check needs **live verification** against this app's multi-port local dev setup (`config/sanctum.php`'s `stateful` list includes `localhost:8080`, `localhost:8081`, etc. — same-site-but-cross-port requests send `Sec-Fetch-Site: same-site`, not `same-origin`) and its permissive CORS config (`config/cors.php` has wildcard `allowed_origins => ['*']` combined with `supports_credentials => true` — a pre-existing oddity, flagged but not something this task fixes unless it actually breaks under the new check).

### Medium-impact guide items

3. **Cache `serializable_classes` hardening** — new default blocks unserializing PHP objects from cache. Four call sites cache objects today. Per your decision: the two `Coi.php` sites (raw `json_decode()` of static JSON definition files, no `true` flag) will be converted to array decoding — a trivial, self-contained fix that removes object caching there entirely. The two Eloquent-Collection sites (`User.php`'s permissions cache, `NextActionAssigneeController.php`) will be allow-listed in the new config instead of refactored, since converting them to arrays risks breaking downstream code that expects model instances — noted as intentional future cleanup in a new `documentation/future-tasks.md`, per your instruction.
4. **`upsert()` with empty `uniqueBy`** — not applicable; both existing `upsert()` calls (`GroupVisibilitySeeder`, `ForeignComponentsRefresh`) already pass non-empty `uniqueBy` arrays.

### Low-impact guide items

- **Session `serialization` config** — no key exists today (implicit legacy `'php'`); no PHP objects are stored in session data anywhere in `app/`. Per your decision: adopt the new `'json'` default now. This forces every currently-active user session to re-authenticate at deploy time — communicate this before shipping, it's a one-time operational cost, not a code risk.
- Everything else in the low-impact list — `Container::call` nullable defaults, `Manager::extend` callback binding, domain-route precedence, polymorphic pivot naming, `JobAttempted`/`QueueBusy` event property renames, pagination Bootstrap view names, `Str` test-factory reset, Eloquent model-boot nested instantiation, custom `Dispatcher`/`ResponseFactory`/`MustVerifyEmail`/cache-contract implementations, password-reset-subject test assertions, `withScheduling()` timing, custom HTTP Client `Response` subclassing, `DeleteWhenMissingModels` — **confirmed absent from this codebase** via exhaustive grep across `app/`, `tests/`, `routes/`, `config/`, `bootstrap/`. No action needed for any of these.

### Package-specific breaking changes requiring code work

**`spatie/laravel-permission` 6→8** (breaking changes land in v7.0.0's modernization pass):
- **Highest risk in this whole upgrade**: `app/Models/Traits/HasRoles.php` re-implements `assignRole()`/`givePermissionTo()` from scratch, calling Spatie's own internal helper methods (`getStoredRole()`, `getStoredPermission()`, `ensureModelSharesGuard()`, `forgetCachedPermissions()`) to inject a custom `ensureInScope()` check tied to a `permissionScope` property. v7 added stricter return/parameter types throughout the trait — if this custom override's method signatures don't match the new parent trait's, PHP will fatal at class-load time (incompatible override), not just misbehave silently. This must be diffed line-by-line against the real vendored v8 `Spatie\Permission\Traits\HasRoles` source *after* the composer update, and re-ported.
- `app/Modules/User/Models/User.php` overrides `hasPermissionTo()`/`getAllPermissions()` with custom caching logic — same signature-compatibility check needed against v8.
- Event classes gained an `Event` suffix (`PermissionAttached` → `PermissionAttachedEvent`, etc.) and commands gained a `Command` suffix (`CacheReset` → `CacheResetCommand`) — confirmed via grep that nothing in this app listens for or references the old names, so no action, but re-grep after the bump as a final check.
- `clearClassPermissions()` (removed in v7) — confirmed unused.
- Custom `App\Models\Role`/`App\Models\Permission` subclasses, the raw `role_permissions_view` SQL view (`database/migrations/2021_12_16_152229_create_role_permissions_view.php`), and direct `role_has_permissions` table writes in `RolesAndPermissionsSeeder`/`GroupRoleAndPermissionsSeeder` all depend on stable table/column names. v7's "modernized migration stubs" are cosmetic per the changelog (package migrations are also guarded against re-running on tables that already exist), but smoke-test a fresh `migrate` in CI/staging to be sure.

**`spatie/laravel-activitylog` 4→5**:
- Requires a new migration: add `attribute_changes` column, drop `batch_uuid` column. Confirmed `batch_uuid` is **never referenced anywhere** in `app/` or `tests/` — safe to drop, no custom data-preservation logic needed. This app never used the package's automatic attribute-change tracking (no model uses the `LogsActivity` trait — all logging goes through the manual `activity()` helper via `app/Listeners/RecordEvent.php` and `app/Actions/LogEntryAdd.php`), so the `properties`/`attribute_changes` column split has no impact on existing data or behavior.
- `app/Models/Activity.php`'s `boot()` override calls `getExtraProperty('activity_type')` — **must rename to `getProperty('activity_type')`**, the one mandatory code change for this package.
- Config renames: `delete_records_older_than_days` → `clean_after_days`; `subject_returns_soft_deleted_models` → `include_soft_deleted_subjects`. The `table_name`/`database_connection` keys are removed entirely in v5 (moved onto the custom `Activity` model's own `$table`/`$connection` properties) — confirmed `ACTIVITY_LOGGER_DB_CONNECTION` isn't set anywhere in `.env`/`.env.example`, and the table name already matches the package default (`activity_log`), so no `$connection`/`$table` override is actually needed on the model — just drop the two keys from config.
- Confirmed **absent** via grep, so no action needed: `CauserResolver` facade usage, `LogBatch`/`Activity::batch()`, `$activity->changes()`, the `LogsActivity`/`CausesActivity` trait's renamed relations (`->activities`/`->actions` — this app rolls its own `logEntries()`/`latestLogEntry()` via `HasLogEntries`), and `Relation::morphMap()` (subject/causer types are stored as raw FQCNs, which v5 doesn't change).
- The `->tap(fn (Activity $activity) => ...)` fluent builder call in `app/Listeners/RecordEvent.php:55` is a different feature from the renamed/removed model-level `tapActivity()` hook — expected to keep working; confirm via the full test suite.

## Implementation

### 1. Branch

Continue on `composer-updates-202609` (same reasoning as the Laravel 12 upgrade — this is a continuation of the same in-flight dependency-upgrade series).

### 2. Composer changes

Only 5 of the ~14 affected packages need an explicit `composer.json` constraint edit — the rest resolve to newer compatible releases within their existing constraints once `--with-all-dependencies` is used (verified live):

```diff
- "laravel/framework": "^12.0",
+ "laravel/framework": "^13.0",
- "laravel/tinker": "^2.5",
+ "laravel/tinker": "^3.0",
- "rap2hpoutre/laravel-log-viewer": "^2.0",
+ "rap2hpoutre/laravel-log-viewer": "^3.0",
- "spatie/laravel-activitylog": "^4.0",
+ "spatie/laravel-activitylog": "^5.0",
- "spatie/laravel-permission": "^6.0",
+ "spatie/laravel-permission": "^8.0",
```

Then, following the same container conventions as the Laravel 12 upgrade:
```
docker compose up -d db redis
docker compose run --no-deps --rm --entrypoint composer app update \
  laravel/framework laravel/tinker rap2hpoutre/laravel-log-viewer \
  spatie/laravel-activitylog spatie/laravel-permission \
  nunomaduro/collision laravel/telescope laravel/sail laravel/fortify \
  laravel/sanctum laravel/slack-notification-channel lorisleiva/laravel-actions \
  spatie/laravel-ignition lab404/laravel-impersonate phpunit/phpunit \
  --with-all-dependencies
```
Listing every affected package explicitly (rather than just the 5 with constraint changes) matches exactly what the dry run verified works — avoids any surprise resolution difference at execution time. After a clean resolve, check `git diff composer.json composer.lock` against the expected package list above before proceeding to code changes (a solver failure or unexpected extra major bump elsewhere is a stop-and-reassess signal, same as last time).

### 3. Code changes (needed before the app will boot correctly)

- `app/Http/Kernel.php:38` and `config/sanctum.php:47` — rename `VerifyCsrfToken` → `PreventRequestForgery` (update `use` imports too).
- `app/Models/Activity.php` — rename `getExtraProperty(` → `getProperty(`.
- `config/activitylog.php` — rename `delete_records_older_than_days` → `clean_after_days`, `subject_returns_soft_deleted_models` → `include_soft_deleted_subjects`; remove the now-unsupported `table_name`/`database_connection` keys.
- `config/session.php` — add `'serialization' => 'json'`.
- `config/cache.php` — add a `'serializable_classes'` allow-list covering exactly the classes round-tripped through the two Collection cache sites (`App\Models\Permission`, `Illuminate\Database\Eloquent\Collection`, the `NextActionAssignee` model class, etc. — enumerate precisely by reading `User.php:85` and `NextActionAssigneeController.php:14` during implementation).
- `app/Modules/ExpertPanel/Models/Coi.php:145,153` — pass `true` as `json_decode()`'s second argument; update any `->property`-style access on the decoded structure elsewhere in the file to array (`['property']`) syntax.
- New file `documentation/future-tasks.md` — note that the User/NextActionAssignee cache sites are allow-listed for now and should move to array-based caching later, per your instruction.
- `app/Models/Traits/HasRoles.php` — after the composer update, diff `assignRole()`/`givePermissionTo()` against the real vendored `Spatie\Permission\Traits\HasRoles` v8 source and re-port the custom `ensureInScope()` injection to match current signatures/internals.
- `app/Modules/User/Models/User.php` — re-verify `hasPermissionTo()`/`getAllPermissions()` overrides against the same v8 trait.

### 4. Verification

Same battery as the Laravel 12 upgrade, plus items specific to this upgrade's higher-risk surface:
- `php artisan about` — boots under Laravel 13.
- `php artisan config:clear && php artisan route:list` — also diff the route list before/after to confirm Fortify's new WebAuthn/passkey transitive deps didn't silently register new routes.
- `php artisan migrate --pretend` first to review the new activitylog migration (adds `attribute_changes`, drops `batch_uuid`) before applying for real.
- Full `vendor/bin/phpunit` suite — pay particular attention to permission/role tests and activity-log tests given the two major bumps; compare against the pre-existing baseline failure set established during the Laravel 12 upgrade (6 errors / 5 failures, all pre-existing/environmental) so any *new* failures are clearly attributable to this upgrade.
- Spot-check `role_permissions_view` still returns correct data post-migration.
- Manually log in through the SPA in the local multi-port dev setup to confirm the new CSRF `Sec-Fetch-Site` check doesn't break login/form submission.
- `npm run build` (unrelated to the PHP bump, part of normal verification; clean up generated `public/build` diffs afterward like last time).

### 5. Commit structure

One concern per commit, per your established convention:
1. `composer.json` constraint bumps (the 5 explicit changes).
2. Regenerated `composer.lock`.
3. CSRF middleware rename (`Kernel.php` + `config/sanctum.php`).
4. Cache hardening: `config/cache.php` allow-list + `Coi.php` `json_decode` array conversion (and any consuming-code adjustments in that file).
5. Session serialization switch (`config/session.php`) — kept separate since it's an operationally distinct decision (forces logout) worth its own changelog entry.
6. Activitylog v5 compatibility: `config/activitylog.php` renames + `Activity.php`'s `getProperty()` rename + the new migration.
7. Permission v8 compatibility: `HasRoles.php` trait re-port + `User.php` override verification — kept as its own commit since it's the item most likely to need iteration during implementation, and should be easy to isolate/revert independently.
8. `documentation/future-tasks.md` addition.
